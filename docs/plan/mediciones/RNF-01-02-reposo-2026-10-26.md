# Medición del RNF en reposo — 2026-10-26

Informe de medición del consumo de memoria y CPU con la barra colapsada. Responde a la pregunta **Q-08** de `docs/plan/ESTADO.md` y documenta la evidencia del hallazgo **H-E1-01**.

- **Trazabilidad**: RNF-01 (RAM < 50 MB), RNF-02 (CPU < 1 % en reposo), E1-CA4, E1-CA5, E2-CA6, A5, Q-08, H-E1-01, R-02.
- **Ejecutado por**: Director de Desarrollo, sobre el binario Release del commit `edbd670` (E2).
- **Estado de la decisión**: pendiente de elección de métrica por el usuario.

---

## 1. Entorno

| Elemento | Valor |
| --- | --- |
| Sistema | Windows 11 Home Single Language, build 26300, x64 |
| CPU | AMD Ryzen 7 3700U, 8 núcleos lógicos |
| RAM del equipo | 33,9 GB |
| SDK | .NET SDK 10.0.401 |
| Runtime | Microsoft.WindowsDesktop.App 10.0.12 (`net10.0-windows`) |
| Binario | `src\StickyBar.App\bin\Release\net10.0-windows\StickyBar.exe` |
| Estado de la UI | Barra colapsada en la pestaña, sin cintas (E2: la UI desplegable llega en E3) |

Sin depurador adjunto, sin Visual Studio, proceso lanzado desde PowerShell.

## 2. Método

1. Arranque del proceso y espera de **8 s** para estabilizar la inicialización (JIT, carga de WPF, primer render).
2. **40 muestras a 1 s** de los contadores `Win32_PerfFormattedData_PerfProc_Process` del proceso `StickyBar`: `WorkingSet`, `WorkingSetPrivate`, `PrivateBytes`, `VirtualBytes`, `PercentProcessorTime`, `HandleCount`, `ThreadCount`. Se usa la clase de CIM en lugar de `Get-Counter` porque sus nombres no dependen del idioma del sistema.
3. **CPU contrastada por delta**: dos lecturas de `Process.TotalProcessorTime` separadas por 30 s de reposo, para evitar el redondeo a dos decimales del contador formateado.
4. **Experimento de reclamación**: `EmptyWorkingSet` sobre el proceso y lectura del *working set* inmediatamente después y 15 s más tarde, para separar memoria residente necesaria de páginas reclamables por el sistema.
5. **Inspección de módulos** para identificar el origen de la porción compartida.

## 3. Resultados

### 3.1 Contadores en reposo (40 muestras, 1 s)

| Métrica | Mín | Media | Máx |
| --- | ---: | ---: | ---: |
| *Working set* | 89,4 MB | **89,4 MB** | 89,5 MB |
| *Working set* privado | 23,1 MB | **23,1 MB** | 23,2 MB |
| Memoria privada comprometida (*private bytes*) | 36,4 MB | **36,5 MB** | 36,6 MB |
| Memoria virtual (espacio de direcciones) | 2.171.835 MB | 2.171.840 MB | 2.171.843 MB |
| Handles | 662 | 664 | 666 |
| Hilos | 18 | 21 | 23 |

La memoria virtual es espacio de direcciones reservado por el runtime y el *driver* gráfico; no es memoria física y no se usa como métrica del RNF.

### 3.2 CPU en reposo

| Medición | Valor | Umbral RNF-02 |
| --- | ---: | ---: |
| Delta de `TotalProcessorTime` en 30 s, sobre un núcleo | **0,16 %** | < 1 % → **cumple** |
| Normalizado por 8 núcleos (estilo Administrador de tareas) | 0,02 % | < 1 % → **cumple** |
| Contador `PercentProcessorTime` formateado | 0,00 % | — |

El dato «CPU < 4 %» que figuraba en la bitácora de E1 no se reproduce: el consumo real es dos órdenes de magnitud menor.

### 3.3 Experimento de reclamación

| Momento | *Working set* | *Working set* privado |
| --- | ---: | ---: |
| Antes de `EmptyWorkingSet` | 89,8 MB | 23,5 MB |
| Inmediatamente después | 0,2 MB | 0,1 MB |
| 15 s después | 5,1 MB | 1,8 MB |

Interpretación: al no haber actividad de UI, el sistema puede llevar casi todo el conjunto de trabajo a la lista de *standby*. Eso indica que buena parte de esos 89 MB no es demanda real: son páginas mapeadas y residentes que el sistema reclamaría con presión de memoria. **No** indica que la aplicación consuma menos: la memoria comprometida sigue siendo la misma (36,5 MB), solo cambia dónde reside.

Por eso este experimento no se usa como argumento para «bajar» la cifra, sino para explicar por qué el *working set* de una aplicación inactiva sobreestima el coste propio.

### 3.4 Composición de la porción compartida

Del *working set* medio (89,4 MB), **66,3 MB (74,1 %) es compartida** y 23,1 MB privada. Los módulos mapeados de mayor tamaño son, por orden:

| Módulo | Tamaño en disco | Origen |
| --- | ---: | --- |
| `System.Private.CoreLib.dll` | 15,28 MB | Runtime .NET |
| `PresentationFramework.dll` | 15,07 MB | WPF |
| `atiumd6a.dll` / `atiumd64.dll` | 13,51 / 12,79 MB | Controlador gráfico AMD |
| `windows.storage.dll` | 8,68 MB | Windows |
| `PresentationCore.dll` | 7,93 MB | WPF |
| `SHELL32.dll` | 7,61 MB | Windows |
| `System.Private.Xml.dll` | 7,42 MB | Runtime .NET |
| `D3DCompiler_47_cor3.dll` | 4,55 MB | WPF / Direct3D |
| `coreclr.dll` | 4,48 MB | Runtime .NET |

118 módulos en total. Ninguno de ellos es memoria privada de la aplicación: se comparten con cualquier otro proceso que use WPF y .NET, y su presencia en el *working set* depende de la presión de memoria del sistema, no del diseño de la aplicación.

## 4. Conclusión

| Métrica candidata | Valor medido | ¿Cumple < 50 MB? | Estabilidad |
| --- | ---: | :---: | --- |
| *Working set* total | 89,4 MB | **No** | Alta, pero incluye 66 MB ajenos y reclamables |
| *Working set* privado | 23,1 MB | Sí | Media: baja si el sistema reclama páginas |
| Memoria privada comprometida | 36,5 MB | Sí | **Alta**: no depende de la residencia de páginas |

La porción que la aplicación realmente ocupa, y que no comparte con nadie, está entre **23,1 MB** (residente propia) y **36,5 MB** (comprometida propia). El umbral de 50 MB del RNF se cumple con las dos métricas privadas; solo se incumple con el *working set* total, que mide en buena parte DLL del sistema.

**Recomendación**: adoptar **memoria privada comprometida** (`PrivateBytes`, 36,5 MB) como métrica del RNF de RAM.

- No depende de la residencia de páginas, así que dos mediciones darán la misma cifra.
- Es la más conservadora de las dos privadas: 13,4 MB por debajo del umbral.
- Deja el *working set* como dato informativo, no como umbral.

## 5. Margen y riesgos

El margen bajo el umbral es de **13,4 MB**, y E1 llegó aquí con una UI mínima. Las etapas pendientes añaden carga:

| Etapa | Qué añade | Riesgo sobre el margen |
| --- | --- | --- |
| E4 | Cintas desplegables y sus elementos visuales | Medio |
| E5 | Iconos de los accesos directos (mapas de bits decodificados) | **Alto**: es el mayor consumidor previsible |
| E7 | Una barra por monitor con el mismo contenido | Alto si se duplican los iconos |
| E8 | Medición del peor caso con todo desplegado | Es la puerta real |

Recomendación de gobierno: fijar un **presupuesto interno de 42 MB** de memoria privada para el peor caso, de modo que E8 tenga 8 MB de holgura, y repetir esta medición al cerrar E4, E5 y E7. Si se supera el presupuesto, las palancas son: decodificar los iconos con `DecodePixelWidth`, limitar la caché de imágenes y compartir el almacén de iconos entre réplicas.

## 6. Reproducibilidad

```powershell
dotnet build StickyBar.sln -c Release
$p = Start-Process .\src\StickyBar.App\bin\Release\net10.0-windows\StickyBar.exe -PassThru
Start-Sleep -Seconds 8
Get-CimInstance Win32_PerfFormattedData_PerfProc_Process -Filter "Name='StickyBar'" |
    Select-Object WorkingSet, WorkingSetPrivate, PrivateBytes, PercentProcessorTime
Stop-Process -Id $p.Id
```

Los valores pueden variar unas décimas de MB entre ejecuciones; la diferencia entre métricas (66 MB de porción compartida) no.

## 7. Decisión adoptada

El usuario resolvió **Q-08** el 2026-10-26:

- **Métrica oficial del RNF de RAM**: memoria privada comprometida (`PrivateBytes`). Medición de referencia en reposo: **36,5 MB**.
- **Métrica de CPU**: delta de `TotalProcessorTime` sobre un núcleo durante 30 s. Referencia en reposo: **0,16 %**.
- El *working set* pasa a ser **dato informativo**, no umbral.
- **Presupuesto interno de peor caso**: **42 MB**, que deja 8 MB de holgura para E8. Se verifica al cerrar E4, E5 y E7.

Consecuencias: `H-E1-01` se cierra y `R-02` pasa a *mitigado*. La interpretación **A5** de `docs/plan/ESTADO.md` queda actualizada con esta definición.
